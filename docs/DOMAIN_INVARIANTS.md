# Domain invariants

Этот документ фиксирует ключевые инварианты доменной модели и границы MVP TeamLab. Они определяют ожидаемое поведение backend и публичного API и дополняют [DOMAIN_MODEL.md](DOMAIN_MODEL.md) и актуальный OpenAPI-контракт.

## 1. ProjectRole

### Роль представляет направление участия

`ProjectRole` описывает роль/специализацию внутри проекта, а не одно вакантное место.

На одной роли могут одновременно находиться несколько участников.

### Специализация уникальна внутри проекта

В одном проекте не может существовать несколько `ProjectRole` с одной и той же specialization.

Инвариант:

```text
unique(project_id, specialization_id)
```

Это обеспечивает однозначный подбор подходящей роли и не ограничивает количество участников на ней.

### `is_open` не входит в модель MVP

У `ProjectRole` нет отдельного состояния открыта/закрыта.

Роль либо существует, либо удалена. Поле `is_open`, соответствующий фильтр и дополнительная бизнес-логика в текущий контракт не входят.

### Контекст текущего пользователя хранится не на роли

Поля, описывающие взаимодействие текущего пользователя с проектом (`my_*` и аналогичный контекст), относятся к project detail и user detail.

`ProjectRole` остаётся описанием самой роли.

### Удаление роли

`ProjectRole` нельзя удалить, если с ней связаны:

* active `ProjectMembership`;
* pending application;
* pending invitation.

Исторические `RoleInterest` и `ProjectMembership`, связанные с удаляемой ролью, в текущем MVP отдельно не сохраняются и удаляются каскадно.

## 2. RoleInterest

### Applications и invitations используют одну модель

`RoleInterest` представляет оба направления взаимодействия:

* application — участник откликается на роль;
* invitation — владелец проекта приглашает участника.

Тип взаимодействия определяется существующим доменным/API-контрактом; отдельные модели `Application` и `Invitation` не требуются.

### Публичные представления разделены по назначению

Публичный API не предоставляет общий список всех `RoleInterest`.

Используются отдельные представления:

* applications;
* invitations;
* notifications.

Notifications являются read-only представлением pending `RoleInterest`, а не отдельной доменной сущностью.

Поэтому отдельные модели `Notification`, `Invitation`, `IncomingInterest` или `Match` в текущем MVP не используются.

### Повторный interest для той же пары не поддерживается

Для одной пары `user/project_role` не создаётся новый `RoleInterest` после `reject` или `accept`.

Уникальность распространяется как на pending, так и на исторические состояния.

### Отмена не входит в MVP

В текущем lifecycle отсутствуют:

* статус `cancelled`;
* cancel endpoint;
* отдельный пользовательский сценарий отмены application или invitation.

## 3. ProjectMembership

### Membership создаётся только после принятия RoleInterest

`ProjectMembership` фиксирует фактическое участие пользователя в роли проекта.

Публичное создание membership напрямую не предусмотрено.

Основной переход:

```text
RoleInterest (accepted)
        ↓
ProjectMembership
```

Membership создаётся backend-логикой в процессе принятия application или invitation.

### Универсальный CRUD для membership не используется

Публичный API не предоставляет:

```text
GET   /project-memberships/
POST  /project-memberships/
PATCH /project-memberships/{membership_id}/
```

Изменение участия оформлено через доменные действия.

### Завершение участия

Поддерживаются два отдельных сценария:

* `leave` — участник самостоятельно покидает проект;
* `remove` — владелец проекта исключает участника.

Для этих переходов используются action endpoints, а не универсальный `PATCH` статуса membership.

### Дублирующее активное участие

Для одного `user/project_role` не должно возникать несколько одновременно действующих membership в тех сценариях, где этот инвариант закреплён текущей доменной моделью и API.

При этом одна `ProjectRole` может содержать несколько разных участников.

---

## 4. Системные справочники

`Field`, `Specialization` и `Skill` являются системными справочниками.

Их наполнение выполняется через:

* admin;
* seed;
* служебные инструменты.

В публичном MVP API эти ресурсы доступны только для чтения.

Публичные операции создания вроде:

```text
POST /fields/
POST /specializations/
POST /skills/
```

не входят в текущий контракт.

---

## 5. Authentication и профиль пользователя

### Login

MVP использует:

```text
username + password
```

Email остаётся пользовательским/контактным полем и не используется как login identifier.

### Изменение specialization

Participant не может убрать или изменить specialization, если существуют:

* active `ProjectMembership`;
* pending application;
* pending invitation.

Исторические записи сами по себе изменение specialization не блокируют.

### Account deletion

Публичный:

```text
DELETE /users/me/
```

не входит в текущий MVP.

Удаление аккаунта требует отдельной бизнес-логики для:

* owned projects;
* memberships;
* interests;
* связанных пользовательских данных.

---

## 6. Project management

Служебные поля:

```text
is_featured
featured_order
```

не управляются владельцем проекта через публичные create/update endpoints.

Они относятся к системному управлению содержимым.

---

## 7. Search

Отдельный глобальный endpoint:

```text
/search/
```

не входит в текущий API.

Поиск выполняется в контексте соответствующего ресурса:

```text
/projects/?search=...
/users/?search=...
```

---

## 8. API contract

Публичные endpoints, поля и статусы должны соответствовать актуальному OpenAPI-контракту.

API-visible поля сверяются с:

```text
teamlab_api_schema_8.yml
```

Lifecycle и доменные инварианты описываются в:

```text
DOMAIN_MODEL.md
```

Этот документ дополняет их правилами, которые особенно важно сохранять при развитии проекта.

---

## 9. Изменения, затрагивающие продуктовый контракт

Следующие изменения не являются локальными техническими деталями и требуют отдельного изменения продуктового/API-контракта:

* явный выбор `role_id` пользователем при application или invitation, если он отличается от текущего механизма matching;
* изменение существующих URL;
* изменение response shape за пределами текущего OpenAPI-контракта;
* добавление новых lifecycle states;
* добавление новых публичных способов создания или изменения `RoleInterest` и `ProjectMembership`.

Такие изменения должны рассматриваться вместе с доменной моделью, OpenAPI и frontend-контрактом.
